# 三个 Agent 应用案例：从知识消费到研发价值

三个案例共用本体、计算语义、资产映射和 SOP，只改变任务契约与工具范围。它们是可实施设计，不是已经运行的系统。示例产品 P/Q、口径和规则均待企业内确认。

## 案例一：指标口径与数据定位助手（首期）

### 价值与边界

用户问题：“产品 P 的核销率应该如何计算、使用哪些数据？为什么报表 A 与报表 B 不一致？”

当前常见成本来自找负责人、翻 SQL、确认粒度和反复澄清业务口径。首期助手交付可追溯的口径差异单和待确认清单。它不生成任意 SQL，不在没有数值证据时宣称已经解释报表数值差额。

### 所需材料和工具

- 批准的领取、核销定义，产品适用规则和负责人。
- 两份报表/指标定义及版本、批准 SQL 引用、资产卡、schema、新鲜度和血缘。
- `get_definition`、`get_mapping`、`search_assets`、`get_asset`、`get_lineage`、`get_approved_sql`、`compare_definitions`。

### SOP

1. 绑定产品、报表版本、统计期和用户权限；缺一项先澄清。
2. 从本体读取领取实例、成功核销、资格和规则版本；只使用 approved 定义。
3. 展开两指标的统计对象、分子、分母、时间、成熟窗口、去重、聚合行为、允许汇总维度、过滤和零分母处理。
4. 沿映射定位批准 SQL、来源资产、完整身份、关联和数据新鲜度。
5. 比较定义和 SQL 结构，把差异分成业务口径、数据实现、数据状态、未知四类。
6. 检查每项差异的证据、版本和覆盖范围；未识别 UDF、宏或无权资产标 unknown。
7. 输出差异单，请数据负责人确认技术实现、业务负责人确认口径含义。

### 输出工件示例

| 项目 | 报表 A | 报表 B | 可确认结论 |
|---|---|---|---|
| 统计对象 | 领取实例 | 去重用户 | 定义不同；不可直接比较 |
| 时间 | 领取批次截至观察日 | 核销发生日 | cohort 与 period 口径不同 |
| 汇总方式 | 从实例级分子/分母重算 | 分渠道比率平均 | 聚合不兼容，后者需复核 |
| 部分核销 | 待业务确认 | 待业务确认 | 证据不足，不能归因 |
| 数据状态 | 资产版本与新鲜度引用 | 资产版本与新鲜度引用 | 仅在工具结果完整时判断 |

最终答复必须分成：已确认差异、可能原因、证据缺口、负责人和下一步。所有主张引用定义/SQL/资产版本，而不是只给一个链接。

### 失败处理和验收

- 定义冲突：停止给单一口径，发起业务评审。
- SQL 解析不完整：提供已识别差异和 unknown 部分，由研发人工核对。
- 资产无权：不泄漏名称或存在性，按平台策略返回受限状态。
- 数据未就绪：报告新鲜度，不给业务下降结论。

用历史真实任务验收：关键口径项识别正确、资产定位和引用正确、未知问题能停止或转人工。效率只比较相同任务范围下的人工基线与辅助模式，记录实际投入和返工。

## 案例二：业务规则变更影响分析（扩展）

### 价值与边界

任务：“权益有效期或守约规则将在日期 D 调整，哪些指标、表、作业、报表和 SOP 需要复核？”

业务本体定位规则作用的对象、关系和事实；映射把它连接到指标和资产；血缘继续追踪技术下游。Agent 生成候选影响清单和证据，负责人决定变更范围与发布。

### 所需材料和工具

- 变更前后规则、适用产品、业务生效时间、历史数据政策和业务 owner。
- 规则到概念/指标/映射的反向引用，资产及作业血缘、负责人和发布状态。
- 第一阶段工具，加 `get_reverse_mappings`、受限深度的 `get_downstream_impact`、`create_review_artifact`（只创建评审工件，不修改生产）。

### SOP

1. 将变更拆成语义差异：条件、对象、时间、例外和结论分别变化了什么。
2. 找到引用规则的概念、事实、指标、映射和 SOP；验证适用产品和有效期。
3. 从受影响逻辑定义沿映射定位资产，再按最新血缘查询技术下游；保留图采集时间、深度、截断和手工依赖缺口。
4. 将影响分为必须修改、需要回归、通知确认、暂不影响，并写出证据。
5. 评估历史重算、双版本并行、数据到达和回退要求。
6. 生成评审工件，由业务确认含义，数据研发确认技术影响，平台/报表 owner 确认发布。

### 输出和验收

输出包含变更语义、受影响模型/资产/作业/报表/SOP、负责人、证据、未知项、验证和回退建议。不得仅输出一张无版本血缘图。

用已完成的历史规则变更做回放，比较候选清单与最终变更记录。度量关键漏项、误报的人工处理成本、负责人定位正确性和评审耗时。血缘动态变化，因此验收记录必须固定采集时间。

## 案例三：新产品数据需求辅助设计（扩展）

### 价值与边界

任务：“新产品 Q 需要建设访问—领取—核销—支付—守约的数据能力，哪些定义和资产可以复用，还缺什么？”

Agent 复用公共业务概念和任务 SOP，但不假定新产品继承旧产品规则。它输出设计候选和验收清单，不直接创建生产表、提交作业或发布指标。

### 所需材料和工具

- 新产品业务流程、规则、事件契约、分析问题、SLA、数据分级和 owner。
- 公共本体、相似产品批准模型、资产目录、数据标准、质量规则和开发规范。
- 第一阶段工具，加模型相似度/结构比较、标准查询和设计工件生成；发布接口不对 Agent 开放。

### SOP

1. 将需求拆为业务对象、事件、事实、指标问题和时效要求，列出未定义项。
2. 在公共本体中匹配概念与关系；对每个候选检查身份、状态、规则和证据是否兼容。
3. 在资产和语义模型中寻找可复用逻辑字段、维度、指标及公共层；记录来源版本和适用限制。
4. 生成差距：新增/扩展概念、事件契约、逻辑数据集、映射、质量规则、指标和 SOP。
5. 给出粒度、完整身份、分层和关联建议；N:N、重试、冲正、迟到与历史变化明确设计。
6. 输出研发任务、依赖、owner、验收样例和发布门槛；由架构、业务、研发和治理评审。

### 输出和验收

输出需求澄清表、复用/不复用依据、候选本体与语义变化、资产设计、映射、质量规则、开发任务和验收清单。任何“可复用”都必须说明复用的语义和版本；字段名称相同不构成依据。

以过去完成的新产品项目回放，评估关键问题提前发现率、设计评审返工、复用判断正确性和人工修改量。没有项目真值时只能做专家评审，不能声称减少开发周期。

## 三个案例的共同 Harness

| 阶段 | 确定性控制 | Agent 能做什么 | 人工责任 |
|---|---|---|---|
| 任务进入 | 服务端身份、任务类型、允许产品与工具 | 识别 SOP、提出澄清 | 用户确认问题范围 |
| 知识获取 | 权限过滤、版本和批准状态 | 选择相关定义与映射 | owner 维护定义 |
| 工具调用 | schema、参数、预算、超时、结果裁剪 | 决定下一项只读调用 | 平台维护权限和接口 |
| 结论生成 | 引用存在、证据覆盖、禁用主张检查 | 组织差异、影响和设计建议 | 业务/研发批准关键含义 |
| 发布反馈 | 任务 ID、版本包、修正记录 | 归类 bad case、建议更新位置 | 负责人决定模型/工具变更 |

模型、SOP、检索和工具共同决定结果。出现错误时按定义错误、映射错误、检索遗漏、工具失败、推理错误或权限/数据状态分类，避免把所有问题都归为“模型不够聪明”。
