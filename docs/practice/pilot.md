# 快速试点清单：用一个真实任务验证价值

首期选择一个产品和“核销率口径与数据定位”任务，只读、辅助模式。目标不是上线通用 Agent，而是证明：业务本体＋计算语义＋资产映射＋SOP 能稳定改善一个实际工作环节。

## 进入条件

- 有 10–20 个脱敏历史任务，包含最终人工答案、使用的定义/SQL/资产和关键澄清；数量可按实际取得情况调整，但必须记录。
- 至少一位数据研发负责技术验收，一位业务/产品负责人负责口径含义；平台同学能确认 Dataphin/MaxCompute 接口与权限。
- 公司允许的内网模型或 Agent 入口明确；若尚无模型，先完成知识和工具准备，不用外部模型处理企业内容。
- 试点不包含自动改 SQL、发布作业、写生产数据或业务操作。

## 分阶段清单

### 0. 冻结基线

- [ ] 定义任务范围、用户、完成条件和不做事项。
- [ ] 选取历史任务，按模板记录人工实际投入、交接、返工及答案来源。
- [ ] 将任务按常见、歧义、缺证据、权限受限、数据异常分组；保留部分任务到最终验收前不参与调试。

**产物**：任务卡、基线表、开发集/保留集清单。不要只记录总耗时；对等待时间和实际操作时间分开。

### 1. 建立最小知识包

- [ ] 为任务涉及的产品、权益方案、领取实例、核销交易等填写本体卡，明确身份、关系、约束和反例。
- [ ] 为两到五个实际口径填写指标卡；锁定人群、时间、去重和零分母处理。
- [ ] 登记相关资产、批准 SQL、负责人、新鲜度和有限血缘。
- [ ] 完成业务定义到资产、字段/SQL和证据的映射；缺口不得用模型猜测补齐。
- [ ] 由业务和数据负责人分别评审并冻结版本。

**产物**：本体、语义、资产、映射和评审记录。数量是起点建议，以覆盖试点任务为准。

### 2. 固化 SOP 和只读工具

- [ ] 将案例一的 SOP 按公司流程补齐，定义每步的输入、工具、输出、检查与异常。
- [ ] 评估 Dataphin 的真实接口、版本、RAM/内部权限和分页；无接口时定义受控导出流程。
- [ ] 建立最小只读适配，先支持资产、血缘、定义、映射和批准 SQL 引用。
- [ ] 工具层区分 denied、missing、stale、partial、timeout；记录来源和覆盖范围。
- [ ] 对平台不可达、无权、未知 UDF、过期定义和冲突口径做失败演练。

**产物**：SOP、工具契约、权限矩阵、接口核验记录和失败处理说明。

### 3. 接入 Agent 并开展影子试用

- [ ] Agent 只读，回答不直接进入生产流程；研发同学先独立完成，再对比 Agent 工件。
- [ ] 每次固定模型、知识包、SOP、工具和资产快照版本。
- [ ] 保存用户问题、澄清、工具状态、来源引用、输出、人工修正和实际投入；不记录不必要的敏感数据或隐藏思维链。
- [ ] 将错误归因到定义、映射、检索、工具、推理、权限或数据状态；修正须回到对应工件。

**产物**：Agent 差异单、轨迹摘要、人工评审和 bad case 分类。

### 4. 验收与扩展决策

- [ ] 保留集由研发盲审；关键定义、资产和引用错误逐条统计。
- [ ] 比较人工基线和辅助模式的实际投入、交接、返工、完成质量及新增维护时间。
- [ ] 业务 owner 确认口径解释，数据 owner 确认资产和 SQL 定位；权限违规为零。
- [ ] 只有收益在不同任务中重复、维护责任明确，才进入规则影响分析；再验证后进入新产品辅助设计。

**产物**：验收报告、继续/修正/停止决定和下一阶段范围。

## 建议指标

| 维度 | 计算方式 | 注意 |
|---|---|---|
| 有效完成率 | 无关键错误且验收人接受的任务 / 可判定任务 | denied/资料缺失单列，不伪装成错误答案 |
| 资产定位正确率 | 正确资产与版本引用 / 输出的资产引用 | 仅给表名但版本错误也算错 |
| 主张引用支持率 | 被证据真实支持的关键主张 / 有引用的关键主张 | 有 URL 不代表支持结论 |
| 适当澄清率 | 必须澄清且确实澄清 / 必须澄清任务 | 同时统计不必要澄清 |
| 人工实际投入 | 阅读、查询、核对、修正的主动时间 | 与排队/等待时间分开 |
| 返工与交接 | 被退回次数、涉及角色数量 | 记录原因，避免只追求少交接 |
| 知识维护成本 | 建模、评审、修正和版本更新投入 | 收益必须扣除长期维护 |
| 权限违规 | 不应访问、返回或泄漏的次数 | 必须为 0，且用负例验证 |

不预设节省 30% 或准确率 95% 等成功数字。先采基线，再由使用者与风险负责人设门槛。样本少时报告逐项结果，不用不稳定百分比包装效果。

## 谁负责什么

| 角色 | 你可推动的工作 | 需要协作的决定 |
|---|---|---|
| 数据研发（你） | 任务选择、资产/SQL盘点、粒度关联、技术映射、SOP草案、回放和成本统计 | 不能独自批准业务事实和企业权限 |
| 产品/业务 owner | 定义、规则、例外、产品绑定和验收 | 不能仅凭文档替代数据实现核验 |
| 数据治理/架构 | 命名、生命周期、影响评审、质量与复用边界 | 与现有标准和平台对齐 |
| 平台/安全 | 接口、身份、权限、部署、日志和审计 | 确认公司版本与开放范围 |
| Agent/模型团队 | 模型入口、上下文、工具调度和评估能力 | 不拥有业务定义和生产发布权 |

## 四周参考节奏

这是资源安排示例，不是交付承诺：第一周冻结任务与材料；第二周完成最小模型和评审；第三周接只读工具和失败演练；第四周影子试用并验收。如果平台接口或业务评审未就绪，先交付静态可追溯差异单流程，不绕过权限赶进度。

## 立即可做的第一步

从最近一个真实的“为什么两个核销率不一致”任务开始，复制 [模板](templates.md) 中的任务卡、指标卡、资产卡和映射卡。先把你能确认的数据侧内容填完，把业务事实、部分核销、冲正、成熟窗口等问题集中交给业务 owner。完成后再写 SOP；这一步本身就能暴露口径和资产治理缺口，即使暂时没有 Agent 也有价值。
