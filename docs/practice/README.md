# 数据研发的 Agent 落地指南

适用对象：已有数仓开发、指标、质量和治理经验，想用 Agent 改善实际工作的数据研发同学。研究核验日：2026-11-01。

先选一个反复发生的任务，把完成任务需要的数据知识、业务定义和操作方法组织好，再让 Agent 使用这些知识与工具。**第一份有价值的产物可以是一张可追溯的口径差异单，不必先建设全域知识图谱。**

本指南以芝麻信用小程序的流量、权益领取/核销、支付、守约为场景背景。具体对象名、规则和标识是建模建议，不是支付宝内部实现。MaxCompute＋Dataphin、公司内网是同一项目聊天已确认的环境背景；部署版本、接口、权限及模型服务仍需在公司内核实。本文没有读取企业资料。

## 最小交付物

在一个产品内，选择“核销率口径与数据定位”这个任务。以现有报表、批准 SQL 和元数据为材料，产出：

1. 业务定义：领取实例、成功核销、统计人群、时间窗口，以及相关规则和负责人。
2. 数据定义：来源资产、粒度、身份键、关联、指标计算及数据新鲜度。
3. 映射：每个业务定义对应的数据证据、计算和规则版本。
4. SOP：澄清问题 → 找批准口径 → 定位数据 → 对比差异 → 检查证据 → 输出结果。
5. 验收记录：能否正确完成历史任务，节省多少核对时间，增加多少知识维护工作。

模型是版本化定义，知识索引是派生物，实际数据和作业状态由受控工具获取。模型变更和业务规则发布仍由相应负责人批准。

这是架构、方法、工具研究和应用设计，不是已部署的 Agent。没有新增合成数据、运行实验或接入公司系统。原有 [客户—订单实验](../../examples/README.md) 独立保留，不用其结果证明这里三个案例有效。

官方资料登记在 [专题参考索引](../../sources/practice-references.json)。该文件是本专题的“主张—来源账本”，不属于公众号文章索引，所以使用独立字段结构；JSON 与链接在本轮单独检查。每个产品能力均应区分“官方文档存在”与“公司环境可用”。本文各项首期范围和试点门槛是项目建议，不是行业标准。
