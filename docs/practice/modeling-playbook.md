# 双向建模操作手册：从工作材料到 Agent 能用的知识

本手册的目标是把你已经会做的需求分析、数仓建模、指标核对与治理工作，变成可复用的定义、映射和 SOP。以下名称是设计示例，不是支付宝内部对象或表结构；实际规则须由业务确认。填写时使用 [配套模板](templates.md)。

## 先分清五种产物

| 产物 | 回答的问题 | 例子 |
|---|---|---|
| 资产模型 | 数据和处理能力在哪里、谁负责、质量怎样 | 哪个作业生成领取明细，报表依赖哪个汇总表 |
| 业务本体 | 业务世界中有什么、如何区分、发生什么、受什么约束 | 领取实例属于某权益方案，核销交易消耗领取实例 |
| 计算语义 | 业务量如何计算和关联 | 按领取批次统计的实例核销率，分母是什么 |
| 映射 | 业务含义如何落在数据上 | 哪些字段定位实例，哪些状态与记录证明成功核销 |
| SOP | 一类任务如何完成和验收 | 口径澄清、定位资产、比对定义、检查证据、输出差异单 |

本体是业务概念及其语义约束的显式模型。首期可用受控 JSON/YAML/表格表达，但必须有稳定身份、关系语义、约束和评审，不能只有术语名称列表。是否采用 RDF/OWL 是后续表达与工具选择，不决定是否认真做了本体建模。

## 第一步：选一个能交付价值的任务

**输入**：近期重复问题、需求单、人工处理记录和使用者。

**做法**：选定一个产品和任务，收集同类历史问题，写清“谁会拿结果做什么”。不要以“抽取所有表”作为目标。首期建议核销率口径与资产定位，先回答定义和数据来源，再决定是否查询数值。

**填写示例**：任务 T-01：“研发同学需要解释产品 P 的两份核销率报表为何不同”；产物为双方定义、SQL/资产引用、可证实差异和待确认问题。实际产品标识在公司内填写。

**通过条件**：有一个愿意验收的人、有历史参考答案或能补齐答案的人，且结果有明确工作用途。

**常见错误**：从“做一个通用问数 Agent”开始；没有任务基线就承诺节省比例。

## 第二步：盘材料并建立证据目录

**输入**：报表定义、批准 SQL、表结构、作业与血缘、产品规则、评审记录。

**做法**：按材料 ID 登记来源位置、版本、负责人、采集时间、权限和覆盖范围。把“业务定义”“代码实现”“实际数据观察”分开。代码存在只能证明实现，不保证业务认可。

**填写示例**：E-RULE-01 定位到核销成功定义和适用产品；E-SQL-01 定位到报表 A 的当前生产 SQL；E-META-01 标记相应 schema 快照。没有业务批准时写“候选”，不反推为事实。

**通过条件**：本任务用到的每条关键结论有可定位来源；冲突和缺失单列。缺公开 API 时，先让有权限的同事导出有限范围元数据，导出物保留时间和版本。

**常见错误**：将爬到的说明、SQL 注释和现行制度赋予同样权威；丢掉资料的适用日期。

冲突不能靠“最新文件优先”自动裁决。业务定义证明批准含义，版本化代码/SQL证明实现，数据观察证明某一快照的状态；三者不一致时并列保留并由对应 owner 处理。证据卡及默认权威边界见[模板](templates.md#2-证据卡与权威边界)。

## 第三步：从数据侧抽取知识

**输入**：第二步材料及任务问题。

**做法**：先写每张数据集“一行代表什么”，再识别完整身份和版本，最后整理关联、计算与质量要求。对同名字段检查命名空间、产品范围及生命周期；事件 ID、业务实例 ID、用户 ID 不可互换。

| 检查项 | 操作方法 | 核销场景示例 |
|---|---|---|
| 粒度 | 用一句话定义一行，区分事实、快照和汇总 | 一次领取实例，或一次核销尝试；不能混为一层 |
| 身份 | 联合唯一性、空值、重用范围、版本验证 | 产品范围是否属于实例 ID 的完整身份，要查契约 |
| 时间 | 区分事件时间、处理时间、分区时间和业务日期 | dt 不一定等于核销发生日 |
| 关联 | 检查基数、孤儿、重复和 as-of 条件 | 一个实例可能对应多次核销记录；先按目标粒度归并 |
| 指标 | 展开人群、分子、分母、过滤和去重 | 实例数核销率与人数核销率是不同指标 |
| 质量 | 判断能否支持任务，明确未到齐和异常处理 | 当日分区未完成，不能拿来判业务下降 |

**通过条件**：给定口径，另一位研发能定位资产并复述计算过程；任何 N:N 或历史关系都说明处理方式。

**常见错误**：直接串联访问、领取、核销、支付明细导致放大；按字段同名关联；把 UV 相加当跨渠道人数。

## 第四步：通过本体数字化业务知识

### 如何识别实体、值与关系

实体需要能跨记录被再次识别，并有值得管理的生命周期；值表达属性的意义和单位。产品、权益方案、领取实例、支付交易、履约义务可作为候选实体；金额、时间、状态码可作为值或受控枚举。不是每个名词都要建实体。

“领取”如果需要身份、领取者、适用规则和有效期，应建模为领取实例或领取事件，而非只加一条用户到权益的无属性边。“支付”要区分订单、交易尝试、支付成功事实；谁付款与谁持有权益也不应默认相同。

| 候选对象 | 需要回答的身份与关系问题 | 规则/反例 |
|---|---|---|
| 产品与权益方案 | 方案是否跨产品共享？版本如何识别？ | 同名方案不一定是同一方案 |
| 访问事件 | 事件去重键、会话和用户如何定义？ | 匿名访问不能直接归并到登录用户 |
| 领取实例 | 谁持有、属于何方案、适用哪个规则版本？ | 同人可多次领取；用户不是实例主键 |
| 核销交易 | 消耗哪个实例、次数/金额多少、结果如何确认？ | 请求提交、页面成功提示未必是最终核销成功 |
| 支付交易 | 属于哪个订单、付款人是谁、是否有撤销/退款？ | 支付成功不等于净收入，不等于已核销 |
| 履约义务 | 谁在什么期限内完成什么义务？ | 义务尚未到期不自动等于违约 |
| 履约事件 | 什么证据证明义务已履行？ | 付款事件是否足够证明履约由具体业务确认 |

### 如何定义关系和约束

用能被证据支持的完整命题写关系，如“领取实例由用户持有”“核销交易消耗领取实例”，并写角色、方向、基数和适用时间。外键只说明可连接，不能证明关系的业务含义。

约束至少分四类：身份/基数约束、业务资格约束、状态转换约束和时态约束。例如“只有成功交易计入成功核销”属于事实判定；“实例已过期不能发起核销”属于操作资格，两者不能混用。历史事实不会因为当前资格变化自动失效。

规则结构采用“对象＋条件＋结论＋例外＋证据＋有效期＋负责人”。区分不满足与未知：缺记录、记录迟到或无权限，不自动判定未核销、未履约。

状态应区分原始系统状态、归一业务状态和截至某时点的派生状态；有效期、剩余次数与核销结果可能是不同维度，不强行塞入单一互斥状态机。变更必须保留旧规则及 as-of 解释。

**通过条件**：业务同学能审查定义和反例；研发能说出证明事实所需的条件。业务未确认的关系保留 candidate。

## 第五步：构建计算语义与融合映射

先定义指标契约，再绑定来源。以下只是候选定义，不是支付宝现行口径：

| 候选指标 | 必须锁定的定义 | 不能自动等价为 |
|---|---|---|
| 产品访问 UV | 产品边界、用户身份、时区、统计期、匿名处理 | 各入口 UV 之和 |
| 领取人数 | 成功领取事实、用户去重、时间归属 | 领取实例数 |
| 领取批次实例核销率 | 某领取期的批准合资格实例中，截至观察时点至少成功核销一次的实例数 / 同批次合资格实例数 | 当日核销交易数 / 当日领取数 |
| 支付成功率 | 按订单还是尝试、成功终态、重试、统计期 | 成功金额 / 应付金额 |
| 到期守约率 | 合资格且已到期义务、按期完成标准、取消/豁免、观察截止点 | 已完成义务 / 全部义务 |

核销率特别确认：有效期不同的批次观察时长不同，跨批次对比需明确成熟窗口；部分核销是否算已核销、冲正后是否撤回，由业务批准。分母为零应返回“不可计算”及分子分母，不默认返回 0%。

同时声明聚合行为：金额在币种、业务定义和时间条件一致时可能可加；期末余额通常只能沿部分维度汇总；UV、比率和 cohort 转化率通常不可直接相加或平均。Agent 切换维度或时间粒度时，必须检查 `allowed_rollups`；不兼容时从批准的基础分子/分母、去重明细或快照重算。跨产品指标即使同名，也要先验证人群、身份和规则兼容。

映射至少区分对象身份映射、属性映射、关系/事实映射、规则检查映射和指标实现映射。每条映射填写证据条件、源字段、转换、完整身份、空值和异常处理，以及业务/资产版本。示例：成功核销事实映射必须找到权威交易记录、成功条件及冲正处理；仅看到 click_redeem 埋点不够。

**通过条件**：可以沿“问题 → 定义 → 指标 → 映射 → 资产/SQL → 证据”逐步追溯；缺映射返回缺口，不能临时让模型猜字段替代。

## 第六步：将方法固化为 SOP，并跨场景复用

SOP 不是泛泛提示词，而是任务契约。公共本体承载共享含义；产品绑定提供适用规则；SOP 复用步骤和验收。例：比较两份核销率报表时，步骤相同，但产品 P 的部分核销规则不能直接套给产品 Q。

复用之前检查概念含义、身份范围、状态终态、规则版本和证据来源是否兼容。参数仅能覆盖模板允许变化的部分；如果事实定义或分母含义改变，新增独立定义/版本并评审，不能只换一个显示名称。

**通过条件**：SOP 每步都有输入、工具或人工动作、输出、失败分支；证据不足时的路径可执行。完整模板见 [SOP 与产品绑定](templates.md#6-sop-任务契约与产品绑定)。

## 第七步：评审、发布、维护

数据研发负责资产、SQL、粒度、关联和技术映射；产品/业务负责人负责业务含义、例外及规则；平台负责授权、接口和引擎接入。一个人可兼任角色，但签认内容必须分开。

candidate → reviewed → approved → deprecated 是本项目建议的知识生命周期。发布包锁定本体、指标、映射、SOP、来源及评审记录版本；有批准不等于永远正确，来源变化触发复核。图和检索索引均可从定义重建。

自动化可以抽取字段、SQL AST、血缘候选、术语候选、定义差异和待评审草稿；不能自动批准实体合并、业务关系、指标分母或生产变更。对自动候选保留抽取器版本、来源和未解决项，confidence 只供排序。

## Ossie 能帮到哪里

基线固定在 [Apache Ossie 48da55a](https://github.com/apache/ossie/tree/48da55a07e4e8c3a11a662b14727557f6342536d)，规范标为开发草案。以下核对自本地规范与代码，不代表公司系统已接入。

| 本指南的产物 | Ossie 对应 | 边界 |
|---|---|---|
| 计算语义 | dataset、field、primary_key、relationship、metric、表达式 | 声明与校验不等于 MaxCompute 执行适配 |
| 业务对象和值 | EntityType、ValueType、extends、identify_by、关系 roles/multiplicity | 身份要由业务批准；不能把 JSON 属性字段照搬为本体概念 |
| 属性与关系 | 通过对象到值/对象的关系表达，必要时显式角色 | 本指南通用卡片不是可直接提交的 Ossie 文档 |
| 数据到业务对象 | concept_mappings、object_mappings、referent_mappings、link_mappings | 复合身份通过 identifying relationships 定位；一个 mapping 文档引用一个语义模型和一个本体 |
| 约束与 SOP | 部分结构及引用可校验 | 完整业务规则、审批、状态推进和 SOP 不由该规范自动执行 |

固定版本 [ontology.md](https://github.com/apache/ossie/blob/48da55a07e4e8c3a11a662b14727557f6342536d/ontology/ontology.md) 的兼容说明仍称独立 mapping 的 parser/converter 支持待补；但同版 [validate.py](https://github.com/apache/ossie/blob/48da55a07e4e8c3a11a662b14727557f6342536d/validation/validate.py) 已有 validate_mapping / validate_ontology 等检查，覆盖引用的文档名称、概念、关系及表达式字段等。应分别核验校验器、SDK、转换器和执行引擎，不能把那句兼容说明解释为“完全没有 mapping 校验”。缺 SQLGlot 或引用不可解析导致的跳过/警告也不能记为完整通过。

Ossie 是可选交换表达：先把业务定义和本地平台实现理顺，再按互操作需求导出适合的部分。不要为了采用一种格式而迁移全部研发平台。
