# Ossie 桥接到数据研发 Agent 的落地方法

## 分层与数据流

```text
业务本体（概念、身份、关系、约束）
              ↓ ontology mapping
逻辑语义模型（dataset、field、relationship、metric）
              ↓ 资产解析/血缘/权限工具
物理数据与执行平台（表、列、作业、SQL、质量快照）
              ↓ SOP 与证据检查
Agent 输出（定义、定位、差异、证据、待确认项）
```

进入模型上下文的是已批准的概念、身份、关系、指标定义、映射版本和证据摘要；实时表结构、血缘、分区状态和权限由只读工具获取；业务批准、权限决策和高风险变更必须保留人工边界。

## 推荐的编译/发布管线

1. 从需求、SQL、DDL、血缘和规则文档抽取候选实体、字段、关系和指标。
2. 数据研发确认粒度、完整身份、连接基数和表达式；业务负责人确认概念、关系、状态和例外。
3. 生成 Ossie ontology、semantic model 和 mapping 三件套，锁定版本及来源。
4. 运行 schema、语义引用、ontology 引用、mapping 闭合和 SQL 语法检查。
5. 生成转换损失报告：精确映射、降级映射、扩展字段、无法映射、待人工确认、往返差异。
6. 只有批准包才能进入 Agent 检索；运行时仍通过资产/权限工具取得最新状态。

## Agent 的最小步骤

以“核销率为什么不同”为例：

1. 根据产品、指标和观察时点选择批准模型版本。
2. 从 ontology 确认“领取实例、核销事实、有效期、冲正”的概念和关系。
3. 从 mapping 定位身份字段、成功条件、关联路径及来源 SQL。
4. 调用只读元数据、血缘和质量工具，核对当前资产是否仍匹配版本。
5. 按 SOP 对比分子、分母、粒度、时间窗口和去重规则。
6. 输出结论、证据链接、差异原因和未决问题；映射缺口时停止猜测并升级人工。

Ossie 在这里是可追溯的交换表示，不是 Agent 的权限系统、查询引擎或推理引擎。

## 维护与验收清单

- 每个概念有稳定 ID、owner、版本和来源。
- 每个实体身份能落到完整字段或递归 referent mapping。
- 每条关系有业务证据；外键和同名字段只作为候选。
- 每个指标写清分子、分母、粒度、时间、去重和允许聚合。
- 静态验证、数据剖面、业务评审和实际执行分别留证。
- 规则或资产变化触发 mapping/SOP 复核，不静默覆盖旧版本。
