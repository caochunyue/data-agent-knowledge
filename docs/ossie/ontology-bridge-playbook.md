# 从资产语义模型构建业务本体：可落地桥接手册

这份手册针对已经有 Ossie `semantic_model` 的数据研发团队。目标不是一次性建立“全业务本体”，而是从一个可验收任务出发，补齐业务概念、身份、关系和约束，再用独立 mapping 把它们落回已有资产语义模型。

## 1. 先确定边界：资产语义不等于业务本体

已有语义模型通常已经回答“表/数据集怎么查”；本体还要回答“业务上什么东西存在、如何识别、发生了什么、关系是否成立”。

| 已有资产语义 | 需要补的本体知识 | 不能直接推断的内容 |
|---|---|---|
| dataset 粒度和主键 | 业务实体及其稳定身份 | 表名就是实体名 |
| field 类型和表达式 | 属性的业务含义、单位、值域 | 字段名就是业务关系 |
| relationship 的 join 列 | 关系名称、角色、基数、有效期 | 外键证明业务事实 |
| metric 公式 | 指标所描述的业务对象和事件 | 指标名证明口径已批准 |
| 血缘和质量结果 | 事实的证据来源和适用范围 | 当前数据状态等于业务规则 |

首期只选择一个业务切片，例如“权益领取—核销—支付”，并把范围写入 `scope`：产品、地区、时间、规则版本、排除项。

## 2. 本体构建的五步法

### 第一步：从一个已用指标反向切片

选一个反复被问、已有批准 SQL、结果可由业务负责人验收的指标。沿 SQL 的分子、分母、过滤和 join，列出候选对象、事件和值类型。

产物是“候选概念表”，每项标注 `candidate`，不直接发布为事实：

| 候选 | 来自资产 | 需要业务确认的问题 |
|---|---|---|
| 领取实例 | `redemption` 明细一行 | 同一用户能否多次领取？产品/租户是否进身份？ |
| 核销交易 | 核销流水一行 | 请求、成功、冲正分别是什么事实？ |
| 有效期 | 开始/结束字段 | 到期按哪个时区、哪个规则版本判断？ |
| 用户 | 用户维表或主体 ID | 匿名、注销、主体合并如何处理？ |

### 第二步：给每个实体写“可复述身份”

不要从 `primary_key` 直接复制。用一句业务命题说明身份，并用数据剖面验证：

```text
领取实例 = (租户, 产品, 领取实例号, 规则版本)
证据：生产契约 + 去重检查 + 历史重用范围
未知：跨产品迁移后的旧实例号是否保留
```

如果实体只能通过另一个实体定位，就使用 identifying relationship；这正是 Ossie `identify_by` 与 `referent_mappings` 的桥接场景。复合身份缺一项时，mapping 必须阻断，不得降级成“看起来唯一”的字段。

### 第三步：区分属性、事件、关系和约束

- **属性**：实体在某时点的值，如金额、状态、有效期。
- **事件**：发生过的事实，如领取、核销尝试、支付成功、冲正；通常需要事件时间和结果。
- **关系**：对象之间可复用的业务命题，如“核销交易消耗领取实例”。
- **约束**：关系成立或操作允许的条件，如“只有最终成功且未冲正才计入成功核销”。

同一字段可能只是原始状态码；要建立“原始值 → 归一业务状态 → 事实判定”的证据链，不能把状态码直接当作本体关系。

### 第四步：让业务负责人审查反例

每个关系至少准备一个成立例、一个不成立例和一个未知例：

| 命题 | 成立 | 不成立 | 未知 |
|---|---|---|---|
| 核销交易消耗领取实例 | 成功终态有实例 ID 且未冲正 | 失败请求或已冲正 | 交易迟到、实例 ID 缺失或无权限 |

“未知”不能自动变成“不成立”。反例审查通过后，才把概念从 `candidate` 提升为 `reviewed`。

### 第五步：发布本体版本，再写 mapping

本体先冻结概念 ID、关系名、身份和约束；随后 mapping 才能绑定到具体 semantic model。资产变化通常只需新 mapping 版本；业务含义变化必须新本体或新规则版本，不能只改字段表达式。

## 3. 从 Ossie semantic 到 ontology mapping 的填写顺序

按“身份 → 属性 → 关系 → 指标”顺序填写，避免先从字段名猜业务关系。

1. **身份**：把 `dataset.primary_key` 与业务完整身份逐项对照；缺少租户/产品/版本时登记缺口。
2. **对象**：用 `object_mappings` 把属性落到 dataset field 或表达式。
3. **引用**：对象由其他对象识别时，用 `referent_mappings` 递归表达 `identify_by`。
4. **关系**：用 `link_mappings` 描述关系两端的对象映射和路径；不能只引用一条 join。
5. **指标**：在 semantic model 中保留公式、scope 和聚合；在本体侧记录它描述的对象/事件及批准规则，必要时用受控扩展保存关联。

每条 mapping 都应有以下登记信息：来源 SQL/文档、semantic model 版本、ontology 版本、适用时间、owner、空值和迟到处理、人工确认记录。

## 4. 可直接执行的首期试点

**范围**：一个产品、一个指标（领取批次实例核销率）、三至五张已有语义数据集。

**两周产物**：

1. 候选概念表：领取实例、核销交易、权益方案、用户、有效期、冲正事实。
2. 本体 v0.1：实体身份、`held_by`、`belongs_to_plan`、`consumes`、`reversed_by` 及四类约束。
3. mapping v0.1：身份字段、成功条件、冲正排除、连接路径和证据卡。
4. 三个历史问题的回放结果：Agent 能否沿“指标 → 概念 → mapping → 资产 → 证据”定位，并在缺口处停下。
5. 变更演练：更换资产字段或规则版本，能否只生成新 mapping/规则并触发 owner 复核。

**验收门槛**：

- 业务负责人能用例外和反例复述本体关系；
- 数据研发能从每个概念追到完整身份和批准资产；
- 静态 schema/引用检查通过，且数据剖面检查单独留证；
- 三个历史问题的结论、证据和待确认项与人工基线一致；
- 任何无证据的字段同义猜测都会输出“缺口”，不会被 Agent 当成答案。

## 5. 角色与维护责任

数据研发维护粒度、字段、SQL、血缘、数据剖面和技术 mapping；业务负责人批准概念、关系、状态终态和例外；平台同学提供只读元数据、权限和版本接口。Ossie 文件是可审计交换工件，审批、权限和生产执行仍由现有平台负责。
