# 数据 Agent 知识库整体信息架构设计

## 意图

把仓库从“文档、JSON、案例、报告并列堆放”改成可按生命周期理解的知识系统：来源证据、规范学习、工程方法、运行资产、评测与交付报告各有边界。

## 目标

- 微信文章知识与 Ossie 规范知识保持独立。
- 顶层每个目录都有明确职责、输入、输出和阅读入口。
- 不移动被 Python 脚本、测试或 JSON `source` 字段直接引用的路径。
- 所有状态页与当前真实证据一致，不把局部窗口观察写成完整文章覆盖。

## 非目标

- 不重写历史文章内容，不伪造全文解析。
- 不更改案例协议、评测用例、脚本接口或企业平台配置。
- 不删除现有文档；本轮采用导航、分层和兼容入口治理复杂度。

## 仓库模型

```text
sources/  → 证据与账本（输入事实）
docs/     → 人读知识（解释、规范、方法、场景、治理）
templates/→ 可填写工件（把方法变成任务产物）
examples/ → 可运行的合成机制示例
evals/    → 金标/行为合同
scripts/  → 导入、校验、评测执行器
tests/    → 回归保护
reports/  → 运行后生成或人工验收的证据输出
```

`docs/` 内部按五个知识面阅读：`wechat/`（渠道证据）、`ossie/`（规范学习）、`topics/`（跨域基础概念）、`practice/`（通用落地方法）、`offline-rd/`（MaxCompute＋Dataphin 场景实践）。`bridge/` 只说明域间映射；`categories/` 是微信内容的分类视图；`collection/` 是采集治理。

## 决策

- **保留原目录名**：脚本与证据文件引用稳定，靠每个目录的 README 与根导航建立体系。
- **来源和报告分离**：`sources/` 仅保存输入证据与账本，`reports/` 仅保存输出结果和验收结论。
- **状态字段优先**：窗口观察、公开搜索、完整全文、覆盖闭合是不同证据等级，状态页必须区分。
- **桥接需要可追溯**：微信观点进入工程建议，必须经过语义/本体、工具权限和评测的独立验证。

## 验收

1. 根 README 能说明整体目标和全部目录职责。
2. 每个主要顶层目录均有 README 入口。
3. `docs/README.md` 能说明所有文档子域、阅读路径和边界。
4. 本地 Markdown 链接校验和现有 20 个单元测试、40 条行为评测均通过。
