# 本体模型构建：从数据证据到业务批准

## 从熟悉的客户与订单出发

Customer 是有身份的业务对象，EmailAddress 是带业务含义的值。邮箱作为客户属性通常足够；只有需要单独管理验证状态、有效期、绑定历史和共享关系时，才考虑独立的 ContactEmail 实体。不能因为字符串可重复或某张表有主键，就自动升级成业务实体。

本例故意让两个客户共用邮箱，并让不同租户复用 customer_id=1、order_id=o1。客户身份是 (tenant_id, customer_id)，而非邮箱或单独客户号。标识在存储、查询、检索、缓存键和评测中都必须完整保留。

## 建议的构建流水线

1. **采集证据**：DDL、主外键、字段注释、作业 SQL、血缘、数据分布、术语表、业务流程和专家确认。对每条证据保留来源和版本；生产探查做脱敏、采样及权限控制。
2. **提出候选**：聚类同名异义和异名同义，候选标注 EntityType/ValueType/关系，但不直接上线。区分 customer、account、payer、recipient。
3. **识别身份**：检查全局/租户内唯一、空值、复合键、合并拆分与缓慢变化。自然键变动时需要身份映射历史，不能重新生成所有对象。
4. **识别关系**：结合 SQL 用法与业务过程提出关系；订单的 customer_id 可能代表下单人，不一定付款人。外键只支持连接可行性。
5. **数据验证**：唯一率、完整率、孤儿率、基数和时态约束；异常样本进入审核队列，而不是让 LLM 自动修复。
6. **人工批准**：域负责人审查定义、反例、证据、映射、影响范围。confidence 是候选排序信号，不是业务正确率；批准不能仅由数值阈值触发。
7. **版本发布**：candidate → reviewed → approved → deprecated；发布包含 ontology、mapping、语义模型、测试快照和变更记录。

以上是本项目的治理建议。Ossie 的概念和映射结构参考固定版本规范，审批流是应用需要增加的工程机制。

## 候选卡与评审

建议字段：候选 ID、名称与别名、定义、类型、完整身份、关系角色、基数、来源字段、表达式、证据定位、confidence、负责人、状态、模型版本、生效时间、反例及测试 ID。修改业务关系含义视为破坏性变更，重跑关联案例并通知下游负责人。

候选：“Order placed_by Customer”；证据为订单数据契约和业务负责人确认，DDL 复合外键提供结构支持。反例：“付款人与下单人不同”。若只有外键，状态保留 candidate；不得宣称已确认 placed_by。

## 约束与时态

逻辑约束（身份、基数）与业务质量规则（未支付订单不能确认收入）分开。RDF 栈可用 [W3C SHACL](https://www.w3.org/TR/shacl/)表达结构约束；本例采用 SQLite 和 Python，不执行 RDF 推理或 SHACL。OWL 的知识推理和闭世界数据校验也不应视作同一件事。

真实企业需要 valid_from/valid_to 和系统记录时间，并明确 as-of 查询；不把“当前客户归属”套用到历史订单。本例只有静态快照，时态治理未实现。

## 本例验证与局限

实体查找按复合身份参数化执行；缺租户必须澄清；共享邮箱不合并客户。关系工具只暴露批准的 placed_by，返回证据与映射版本。examples/model.json 的 approval 是合成数据契约状态，不是现实审批系统。

更进一步的验收：准备同名不同实体、复合键冲突、身份合并、N:N 关系、历史角色变化、失效映射。由专家制作不参与提示的金标，评估实体对齐 precision/recall、关系事实准确率及证据充分度；不能用“图节点数越多”衡量本体质量。

## 什么时候值得建设完整本体

单个域指标问答优先规范字段与口径；跨域出现客户/账号/组织身份冲突，或需要沿业务关系追踪对象，才增加本体能力。图存储只是实现选择，可先用关系表和版本化定义证明收益。不要从全公司所有表一次性自动生成全局本体。
