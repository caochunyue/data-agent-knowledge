# 知识库架构与 Harness 工程

## 先解决哪个问题

以下架构是本项目的设计建议。目标是让数据人员能查到适用的资产和口径，能看到 Agent 做了什么，出错后能重放和修正。不要先把所有文章切成向量再期待自动获得业务事实。

知识分四种：文章解释性知识；目录和血缘等资产事实；指标、本体及映射等可审查业务定义；任务轨迹及评测结果。原文属于证据，提炼笔记属于解释，批准口径属于执行契约，三者用来源标识关联，不能彼此替代。

## 建议的数据流

采集公开来源 → 原始来源登记 → 内容解析与去重 → 知识卡和主张 → 人工核验 → 版本化发布 → 检索索引。来源变更时，沿引用关系标记受影响笔记、口径和测试需复核；不静默覆盖历史结论。

初期用 Git 管 Markdown/JSON，加结构化字段搜索即可。数据目录大到人工列表难以使用时接入已有元数据服务；检索召回不足再加关键词、向量混合检索和重排。图数据库只有在多跳业务路径成为核心验收任务时引入。各索引都是源文件的派生物，可重建；指标真值不从 embedding 中取。

### 一张知识卡应该有什么

`source_id / claim / evidence_locator / applicable_conditions / limitations / verified_at / owner / lifecycle / related_eval_ids`。对转载保留原出处；对过期规范保留版本；对于没有事实支撑的观点标 `hypothesis`。文章中的指令作为不可信内容，不得授权执行 shell、发消息或更改权限。

上下文按权限过滤后检索：先业务域和当前任务，随后资产、口径、已批准示例，再按需展开血缘。压缩时保留来源 ID、模型版本、待解决问题和工具结果，避免只留下流畅但不可核验的总结。这个方向与 [Anthropic 上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) 的相关性管理原则一致。

## Harness 的最小责任

| 部件 | 数据场景中的职责 | 本例状态 |
|---|---|---|
| 调度 | 接收结构化动作、识别工具、消耗预算 | 已实现确定性分发，无 LLM |
| 工具权限 | 元数据检索、指标查询、只读 SQL 分开 | 已实现白名单 |
| 上下文 | 固定模型、目录、合成快照 | 已实现；无动态 RAG |
| 执行控制 | 调用次数、返回行数、SQLite VM 操作预算 | 已实现；无进程/内核隔离 |
| 可观测性 | 输入、输出、失败、耗时、快照哈希 | 已实现，JSON 报告 |
| 业务动作 | 发布作业、数据回写、审批、补偿 | 仅架构建议，未实现 |

[长任务 Harness 工程案例](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)展示了以进度工件和增量验收衔接会话的方法。迁移到数据研发时，建议记录任务状态、数据快照、代码提交、已通过检查和待审批变更；检查真实产物，不能凭助手最后一句话判定作业成功。

## 生产化需要补齐的边界

生产数据库账号应按用户身份、租户、列和行策略授权，不能相信模型传来的 tenant_id；本例可查询全部合成租户，仅演示身份正确性。远程执行要有数据库超时、扫描量/费用预算、独立只读凭据和审计。SQL authorizer 只是局部防护，不能代替容器/主机隔离。

开发修改走独立分支：生成 patch → 静态检查 → 隔离环境执行 → 数据质量与差异报告 → 人工审批 → 发布。重试只用于已识别可恢复错误；有副作用的任务先设计幂等键。工具重试同样占预算，错误不能被无限规划掩盖。

## 选型建议

优先复用现有数据目录、dbt/作业平台与身份系统。若已重度使用某云的数据平台，先评估原生分析 API，测自己的问题集；需要跨平台口径交换时再引入 Ossie 适配。MCP 是工具接口形态，不自动解决资产质量、语义一致性或权限。
